# Phonon competitor audit: 2026-08-26

## Verdict

Phonon is a local voice-typing product with no Action Mode equivalent. Its pipeline is Parakeet ASR → dictionary retrieval → Gemma 4 E2B correction → clipboard/typing. It has no equivalent of Velora's cross-app planner, verifier, or target-window ownership, so it does not explain the current Action Mode failure.

There is one high-confidence efficiency idea worth implementing as an experiment: reuse and reset the MLX-LM streaming detokenizer instead of reconstructing it for every cleanup request. On this Mac, Velora's installed `mlx-lm==0.31.3` and current Qwen tokenizer took a median **93.21 ms** merely to construct the detokenizer; reset took a median **0.0001 ms**. Phonon's author independently measured a **136.1 ms median wall-time reduction** with the same class of change on its Gemma tokenizer. This measures construction cost only; Velora's end-to-end saving remains untested.

Do not replace Qwen with Gemma based on Phonon's README. Velora's existing Gemma 4 bakeoffs found worse Action reliability, and the exact Phonon E2B PTQ artifact has not been run through Velora's suite.

## Transferable ideas, ranked and falsified

### P0: Reuse the MLX streaming detokenizer

Implement a clean-room, instance-scoped detokenizer cache inside Velora's serialized cleanup worker; call `reset()` for every generation. Add a red test that proves raw token IDs, decoded text, Action JSON, repair output, cancellation, and model reload are unchanged before taking the optimization.

Why it may be wrong: the detokenizer is mutable, and Phonon's process-wide class monkey-patch could contaminate a second tokenizer or a future concurrent request. Tool parsing or a model reload could retain state. The local 93 ms constructor result does not prove 93 ms lower UI latency. Reject the change if output equivalence or lifecycle tests fail; do not copy GPL code.

### P1: Pin every shipped model revision

Resolve each Hugging Face model to an exact revision in the registry and record that revision in diagnostics. Upgrade pins deliberately with a rollback path. This targets reproducibility and release parity, not speed.

Why it may be wrong: pins can preserve upstream defects and complicate security/compatibility fixes. Falsify it by exercising clean install, existing-cache migration, offline start, corrupt-cache recovery, and rollback before release.

### P1: Benchmark the exact Phonon Gemma E2B only as a cleanup candidate

Run `mlx-community/gemma-4-e2b-it-4bit@238767…` through Velora's cleanup, multilingual, Romanization, long-audio, saved-audio, latency, and active-memory gates after the detokenizer experiment. Do not use it for Action without independently clearing the Action suite.

Why it may be wrong: Velora's prior **different** E2B QAT candidate had 5/27 cleanup failures, two regressions, 15.8% slower p50, and about 2.5× the active memory of compact Qwen; prior Gemma E4B also lost Action cases. Phonon's exact PTQ/group-64 conversion could behave differently, but a second cleanup model can add disk, model-swap, and memory costs. Existing evidence is a reason to benchmark, not to switch. See `docs/research/2026-08-21-lightweight-cleanup-planner-bakeoff.md:116-162,187-249` and `docs/research/2026-08-20-gemma4-e4b-qat-mlx-bakeoff.md:77-140`.

### P1: Turn opt-in corrections into a reproducible dogfood corpus

Extend existing history with an optional intended transcript and retain per-phase timings. Use it to replay real failures against model/runtime candidates rather than expanding synthetic deterministic rules.

Why it may be wrong: intended text, audio, and app context are sensitive, and annotation can become unusable toil. Keep collection off by default, use the existing retention/deletion controls, never persist raw screen context, and abandon the field if annotation and replay rates stay too low to affect decisions.

### P2: Experiment with overlapping cleanup and STT loading

On high-memory Macs with both artifacts cached, load cleanup concurrently while preserving STT priority and raw dictation fallback. Gate by device memory rather than making both models mandatory as Phonon does.

Why it may be wrong: simultaneous MLX initialization can contend for CPU, SSD, Metal, and unified memory, delaying the first usable dictation while improving only full-ready time. Reject it unless time-to-STT-ready, full-ready, peak RSS, and first-request latency improve on 16 GB and higher-memory machines.

## Reproduction notes

The local detokenizer microbenchmark loaded only the tokenizer from Velora's current cached Qwen snapshot, constructed `tokenizer.detokenizer` seven times, then called `reset()` seven times. It did not load model weights, generate text, modify product state, or test end-to-end UI latency. Timings were 91.66–97.93 ms per construction and approximately 0.0001 ms median per reset. Any implementation must first add output-equivalence coverage and then measure real request latency.

This audit deliberately excludes README adjectives, incomparable vendor GPU benchmarks, and uncommitted claims. It treats upstream source at the audited commit, exact model revisions, official model/runtime documentation, and reproducible local measurements as evidence.
