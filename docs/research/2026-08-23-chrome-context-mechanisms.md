# Reading Chrome's active tab (URL, title) from Velora — root cause + mechanisms

Research date: 2026-08-23. Machine: macOS 26 (Darwin 25), Google Chrome 151.0.7922.173.
Method: Chromium source (GitHub mirror of `chromium/chromium@main`, current as of commit `ba06fb50`, 2026-08-23), web sources, and **direct probes on this machine** (a trusted AX client running `AXUIElementCopyAttributeValue` and `AEDeterminePermissionToAutomateTarget` against Chrome/Safari/Finder/Zen/Slack).

## TL;DR — the root cause of BOTH errors was local, not a Chrome/macOS policy change

**Chrome had auto-updated on disk (151.0.7922.140 on Aug 19 01:14, then 151.0.7922.173 on Aug 21 03:36) while the running Chrome process was never relaunched.** The process observed on Aug 21–22 was executing a binary that had been replaced/deleted underneath it. macOS 26's TCC/AX attribution fails closed against such a process: Apple Events consent is refused promptlessly (**-1743**) and the process's accessibility server refuses every client (**-25211**), while every other (non-stale) app behaves normally. Chrome was relaunched today at 09:35:05 and **both symptoms are gone**, verified empirically:

```
AXIsProcessTrusted: true
AE  com.google.Chrome: -1744   <- "not yet asked" — same as Safari/Slack/Zen. NOT -1743.
AE  com.apple.Safari:  -1744
AX  com.google.Chrome pid=21199 focusedWindow=0 role=0 roleVal=AXApplication   <- AX works
```

Timeline evidence (verified on this machine):

- `/Applications/Google Chrome.app/.../Versions/` contains both `151.0.7922.140` (mtime Aug 19 01:14) and `151.0.7922.173` (mtime Aug 21 03:36); `Contents/MacOS/Google Chrome` was rewritten Aug 21 03:36:48.
- `~/Library/Application Support/Google/Chrome/Last Version` and all three `Singleton*` files are stamped **Aug 23 09:35:05** — the last Chrome launch was this morning. The failures were observed Aug 21–22; the only state change between then and my healthy probes today is the Chrome process itself, and a process observed failing on Aug 21–22 that was still alive from before Aug 21 03:36 was by definition running a replaced binary.
- Current process (PID 21199, started Aug 23 09:35:04) maps the .173 framework (lsof), and responds normally.

Corroboration that this failure class is known: the Keyboard Maestro wiki's troubleshooting page states Chrome's auto-update "frequently breaks the AppleScript connections" and that restarting Chrome resolves it (https://wiki.keyboardmaestro.com/Troubleshooting); Mac admins deploy forced Chrome relaunches after updates because Chrome keeps running the old version until relaunch (https://community.jamf.com/t5/jamf-pro/force-chrome-relaunch-after-update/m-p/342965).

### Root cause per error

**-1743 (`errAEEventNotPermitted`), promptless, Chrome-only, surviving `tccutil reset AppleEvents`:**
To show the Automation consent prompt, TCC must attribute and validate the *target* app (bundle identity + code requirement of the running process). The stale Chrome process's dynamic code no longer validated against the replaced on-disk bundle (the sealed Info.plist/version changed), so tccd failed closed and returned deny without ever prompting — which also explains why the reset didn't help (there was no deny record to clear; the denial was recomputed each time). Mechanism-level detail is inferred (Apple's TCC internals are closed), but the differential facts prove it was per-target state of that process: `AEDeterminePermissionToAutomateTarget` returned -1743 for Chrome and -1744 for Safari/Slack/Zen *from the same client at the same moment*, and after Chrome's relaunch the same probe returns -1744 for Chrome too. Background on -1743/-1744 semantics since Mojave: https://developer.apple.com/forums/thread/106949 and https://developer.apple.com/forums/thread/122573.

**-25211 (`kAXErrorAPIDisabled`) on every AX call including `AXManualAccessibility`/`AXEnhancedUserInterface` sets:**
This error is produced by the HIServices AX layer *inside the target process* before any Chromium code runs — which is exactly why `chrome://accessibility` showed all modes OFF and "Active assistive technology: Uninitialized" (nothing ever reached Chrome's auto-enablement hooks, so there was nothing to wake), and why even attribute *sets* failed. Same stale-process trigger, same recovery on relaunch (verified: first AX call to the fresh process succeeded with no prior enablement). Current Chromium `main` contains **no code path that returns APIDisabled to clients** — the only occurrence of `kAXErrorAPIDisabled` in the tree is in Chromium's own AX-client tooling (`ui/accessibility/platform/inspect/ax_element_wrapper_mac.mm`), confirming the refusal came from the OS layer, not a Chrome feature.

## A. How Chromium's on-demand macOS accessibility enablement actually works

All from `chrome/browser/chrome_browser_application_mac.mm` (https://github.com/chromium/chromium/blob/main/chrome/browser/chrome_browser_application_mac.mm), verified present as strings in the installed Chrome 151 binary:

1. **VoiceOver:** detected directly via KVO on `NSWorkspace.voiceOverEnabled` (set up in `content/browser/accessibility/browser_accessibility_state_impl_mac.mm`). Enables full screen-reader mode.
2. **`AXEnhancedUserInterface`** (set on the app element by non-VoiceOver AT): handled in `accessibilitySetValue:forAttribute:` (~line 464). Requests are counted and **debounced for 2 seconds** (`enableScreenReaderCompleteModeAfterDelay:`, ~line 425) because Sonoma produces spurious flips. Then screen-reader-complete mode turns on.
3. **The "platform API consumers" trigger — this is the one Velora can use:** reading the app element's **`AXRole`** (`accessibilityRole` override, ~line 480). Any trusted AX client that fetches `kAXRoleAttribute` on Chrome's application element causes Chrome to create a scoped accessibility mode (`ui::AXMode::kNativeAPIs | kFromPlatform` on macOS 14+ under the `SonomaAccessibilityActivationRefinements` feature, `ui::kAXModeBasic` otherwise). No screen-reader registration needed. Verified empirically: my role read returned `AXApplication` and web-content AX activates from there.
4. **`AXManualAccessibility` is Electron-only.** Chromium's `accessibilitySetValue:` handles *only* `AXEnhancedUserInterface`; `AXManualAccessibility` appears nowhere in chromium/chromium (GitHub code search: 0 hits). It's an Electron addition: https://www.electronjs.org/docs/latest/tutorial/accessibility/. Sending it to Chrome is a no-op even when Chrome is healthy.
5. **Kill switches:** `--disable-platform-accessibility-integration` (defined in `content/public/common/content_switches.cc` ~line 211: "Disables the activation of browser and web accessibility via interactions with the platform's accessibility integration") and the equivalent `chrome://accessibility` checkbox "Suppress automatic accessibility enablement from platform API consumers such as assistive tech" (`chrome/browser/resources/accessibility/accessibility.html` ~line 150; wired via `SetActivationFromPlatformEnabled(false)` in `content/browser/accessibility/browser_accessibility_state_impl.cc` ~line 334). On the user's machine this checkbox was **unchecked**, i.e. auto-enablement was active — consistent with the block being below Chrome. `--force-renderer-accessibility` force-enables at launch (docs: https://chromium.googlesource.com/chromium/src/+/main/docs/accessibility/overview.md).

**What changed in 2025–2026:** nothing that gates AX *clients*. The "performance filtering"/deferral work is about which AXMode bundle gets enabled per detected AT (and `AccessibilityPerformanceFilteringAllowed` is the only related enterprise policy, in `components/policy/resources/templates/policies.yaml`). Google's agentic-security work (Gemini in Chrome) is entirely about web-side threats — prompt injection, origin sets, user confirmations — and does not touch macOS AX or Apple Events: https://blog.google/security/architecting-security-for-agentic/ (Dec 8 2025), https://9to5google.com/2025/12/08/gemini-chrome-agentic-security/. A trusted client's reads returning APIDisabled is therefore never a deliberate Chromium behavior; it means the OS-level AX transport to that process is broken (stale process; on macOS 26 also seen after TCC/signing hiccups, cf. yabai on Tahoe: https://github.com/asmvik/yabai/issues/2705).

## B. Is there a new Chrome gate on AppleScript/Apple Events? No.

- **No enterprise policy exists** for allowing/denying AppleScript or Apple Events. The complete Chrome policy index (`components/policy/resources/templates/policies.yaml`, current main) contains no entry matching AppleScript/AppleEvent/Automation. Nothing like "AllowAppleScriptAutomation" exists, so there is no `defaults write com.google.Chrome ...` managed-preference override to set. (Chrome does read genuine policies from macOS managed preferences — https://support.google.com/chrome/a/answer/7517624 — but there's no relevant policy to write.)
- The **only** Chrome-side gate remains the old one: **"Allow JavaScript from Apple Events"** (View > Developer menu), off by default since 2018 for security (https://www.chromium.org/developers/applescript/, https://issues.chromium.org/issues/40092604). It is stored as the Chrome pref `browser.allow_javascript_apple_events` (`chrome/common/pref_names.h`) — a Chrome Local State/profile pref, not a macOS defaults key, not a policy. **It gates only `execute javascript`**; `get URL of active tab of front window` and `get title of ...` are unaffected. When it does block, the error is a misleading "Chrome is not running" / "JavaScript through AppleScript is turned off", not -1743 (https://github.com/modelcontextprotocol/mcpb/issues/34).
- Chrome 151's release notes contain no AppleScript/Apple Events/accessibility-gating changes (https://developer.chrome.com/release-notes/151, https://developer.chrome.com/blog/chrome-151-beta); Chrome's `Info.plist` still declares `NSAppleScriptEnabled = true` and its entitlements contain nothing automation-related (verified locally with `codesign -d --entitlements`).
- **macOS 26 added no per-target automation protection for browsers.** The macOS Tahoe 26.x release notes contain nothing on kTCCServiceAppleEvents/AX policy changes (https://developer.apple.com/documentation/macos-release-notes/macos-26-release-notes), and empirically the standard semantics hold on this machine: after `tccutil reset AppleEvents`, all targets including Chrome return -1744 ("would require consent") from `AEDeterminePermissionToAutomateTarget(..., askUserIfNeeded: false)`.
- An AppleScript-driven Chrome automation write-up from Feb 2026 confirms plain AppleScript tab control still works on current Chrome: https://dev.to/haoyang_pang_a9f08cdb0b6c/the-browser-automation-cheat-code-nobody-talks-about-applescript-chrome-52ha.

No 2025–26 issues about Chrome AX breaking specifically; the Tahoe-era problems are TCC grant flakiness for the client itself (https://github.com/asmvik/yabai/issues/2705) and Chrome window-title instability (https://github.com/Hammerspoon/hammerspoon/issues/3721) | — |

Pattern: **time-trackers and launcher utilities use AppleScript; dictation/context tools use AX; password managers use an extension + native messaging.** Nobody uses ScreenCaptureKit/App Intents for the URL.

## D. Ranked mechanisms for Velora (signed, AX-trusted, not sandboxed)

### 0. First, handle the actual failure: detect the stale-Chrome state
Whatever mechanism we pick will die again on Chrome's next auto-update until the user relaunches Chrome. Detect and degrade gracefully:
- Staleness check (cheap, no permissions): compare `NSRunningApplication` for `com.google.Chrome` — if `launchDate` < mtime of `/Applications/Google Chrome.app/Contents/MacOS/Google Chrome`, the running process predates the on-disk binary → treat -1743/-25211 from Chrome as "stale Chrome", show "Restart Chrome to re-enable browser context" (optionally offer `open -a "Google Chrome" chrome://restart`).
- Never interpret promptless -1743 from a stale target as "user denied"; don't burn the one-time consent UX on it.

### 1. AppleScript / Apple Events (recommended primary — the Timing/Raycast/BTT path)
Gets the exact full URL and title. Steps:
- Send `tell application id "com.google.Chrome" to get {URL, title} of active tab of front window` (scripting-definition reference: https://www.chromium.org/developers/applescript/, https://gist.github.com/vitorgalvao/5392178). Same dictionary works for Chromium forks (Brave/Edge/Arc/Vivaldi) under their bundle ids; Safari via its own dictionary; Firefox/Zen have no tab scripting — fall back to AX/window title.
- Requirements: `NSAppleEventsUsageDescription` in Velora's Info.plist (prompt string); for hardened-runtime distribution builds the `com.apple.security.automation.apple-events` entitlement (without it: instant -1743, no prompt — same symptom, different cause; add it to `make-dmg.sh`'s entitlements next to audio-input); user clicks Allow once on the kTCCServiceAppleEvents prompt (System Settings > Privacy & Security > Automation thereafter). Consent background: https://developer.apple.com/forums/thread/106949.
- Probe consent state promptlessly with `AEDeterminePermissionToAutomateTarget(..., askUserIfNeeded: false)`: -1744 = not asked yet (ask at an opportune moment), 0 = granted, -1743 = denied *or stale target* (disambiguate with the staleness check; if genuinely denied, deep-link to `x-apple.systempreferences:com.apple.preference.security?Privacy_Automation`).
- Do NOT use `execute javascript` — that's the only part gated by View > Developer > "Allow JavaScript from Apple Events" (pref `browser.allow_javascript_apple_events`; no policy/defaults override exists). URL/title reads don't need it.

### 2. Accessibility API (fallback — no new permission, we already hold AX trust)
- Title: `AXFocusedWindow` → `AXTitle` on Chrome's app element — works even with renderer accessibility off (verified).
- URL: first read `kAXRoleAttribute` of Chrome's **application element** — that is the exact documented trigger for Chrome's auto-enablement (`accessibilityRole` override in `chrome_browser_application_mac.mm`; enables `kNativeAPIs|kFromPlatform` on macOS 14+). Then walk the focused window to the `AXWebArea` and read its `AXURL`/`AXDocument` attribute (full URL); the omnibox text field's `AXValue` also works but is display-elided. Allow one retry ~100–500 ms after the role read for tree construction; setting `AXEnhancedUserInterface=true` also works but flips Chrome into full screen-reader mode (heavier) after a 2 s debounce — prefer the role read. Don't bother with `AXManualAccessibility` — Electron-only (https://www.electronjs.org/docs/latest/tutorial/accessibility/).
- Caveats: -25211 from Chrome ⇒ stale Chrome (see 0); slightly higher latency on first use; per-tab URL only for the focused tab (fine for us).

### 3. Chrome extension + native messaging (the 1Password path — most robust, most friction)
`chrome.tabs` in an extension + `chrome.runtime.connectNative` to a Velora helper; verify extension ID and browser signature like 1Password does (https://support.1password.com/1password-browser-security/; Google's recommended alternative to Apple Events scripting: https://www.chromium.org/developers/applescript/). Immune to TCC/AE/stale-process quirks (the extension lives inside Chrome), works in Firefox/Zen too, gives events (tab switches) rather than polling. Cost: publishing an extension, asking users to install it, a native-messaging host manifest, and an IPC helper. Right choice later if browser context becomes a headline feature; overkill today.

### 4. Not recommended / not viable
- `--force-renderer-accessibility`: needs Chrome relaunched with the flag — not something a third-party app can impose.
- ScreenCaptureKit + OCR of the omnibox: needs Screen Recording permission, fragile, no full URL (Wispr Flow uses screenshots for *context*, not for URL extraction).
- App Intents / Shortcuts: Chrome on macOS exposes no "get current tab" intent (nothing in Chrome 151 release notes; no evidence found).
- Waiting for an enterprise policy or `defaults` override: none exists (see B).

## Answers to the specific sub-questions

- **Exact trigger for Chrome's auto-enablement that works for non-screen-reader clients:** read `kAXRoleAttribute` on Chrome's application AXUIElement (any TCC-trusted AX client). Source: `accessibilityRole` override, `chrome/browser/chrome_browser_application_mac.mm` (~line 480). Verified working on this machine against Chrome 151.
- **"AllowAppleScriptAutomation"-style enterprise policy:** does not exist; no AppleScript/AppleEvents policy in `policies.yaml`; nothing to `defaults write`.
- **Does Chrome honor `defaults write com.google.Chrome` for this:** only real policies are honored via managed preferences, and there is no such policy; the JS-from-Apple-Events toggle is an internal Chrome pref, not a defaults key.
- **Why -25211 instead of waking Chrome:** the refusal happens in the OS AX transport before Chromium code runs, so the wake-up hooks (`accessibilityRole` / `AXEnhancedUserInterface`) never execute — consistent with "Active assistive technology: Uninitialized". In our case the transport was broken by the stale-process condition; fixed by relaunching Chrome.
