# LFM2.5-2.6B audit — keep Qwen3.5-4B as the cleanup/action default

**Date:** 2026-08-04 (model released the same day)
**Candidate:** `LiquidAI/LFM2.5-2.6B` (8-bit MLX, official `LFM2.5-2.6B-MLX/8bit`)
**Baseline:** `mlx-community/Qwen3.5-4B-MLX-8bit` (current 24 GB-tier default)
**Verdict: rejected for both pipelines.** Faster and smaller, but it cannot
stop reasoning, and quality collapses in our latency envelope.

## Why it looked promising

- 2.69B params (~2.8 GB at 8-bit vs Qwen's 4.8 GB); hybrid conv/attention
  gives real speed: prefill ~6.9k tok/s vs ~1.9k, decode 121 vs 73 tok/s,
  TTFT 91 ms vs 165 ms in the engine benchmark.
- HF card beats Qwen3.5-4B on AIME25 / IFBench / BFCLv4 — but those scores
  are measured WITH full reasoning traces.

## The structural problem

LFM2.5-2.6B is a **pure reasoning model**: the chat template unconditionally
ends the generation prompt inside an open `<think>` tag, `enable_thinking`
is ignored, and unlike the 1.2B line there is **no Instruct variant** at
2.6B. Force-closing the block (`<think>\n\n</think>`) does not stop it: the
model reasons anyway, in the visible answer channel, then emits a stray
`</think>` and only then the answer. Trained behavior beats the template.

## Cleanup benchmark (26 cases × 3, engine harness, greedy like prod)

| | Qwen3.5-4B-8bit | LFM2.5-2.6B-8bit (think closed) |
|---|---|---|
| quality failures | **0 / 26** | **20 / 26** |
| p50 wall | 650 ms | 493 ms |
| p50 TTFT | 165 ms | 91 ms |
| active memory | 4.41 GB | 2.74 GB |

30 of 78 LFM generations hit the token ceiling (reasoning consumed the
`max(96, input×1.8)` budget → raw fallback); most others tripped the ratio
guard for the same reason. Romanization ignored; "three thirty"→3:30 and
"forty two thousand dollars"→$42,000 conversions missed even in clean runs.
Thinking left ON: 443 think tokens / 4.4 s for a one-sentence cleanup —
7× our p50 budget before the answer starts.

## Action Mode eval (8 scenarios through the real ActionSession, greedy)

| | qwen | lfm think-skip | lfm thinking ON |
|---|---|---|---|
| clean turns | 6/9¹ | 6/9¹ | 4/9 |
| `sends` bit correct on send commands | **2/2** | 0/2 (parse fail) | **0/2 (marked false)** |
| p50 / p95 per turn | 1.76 / 1.88 s | 1.05 / 1.85 s | 3.51 / 7.31 s |

¹ several "failures" are over-strict harness checks (multi-turn caution);
the LFM failures are not: protocol shape errors (`unknown verb 'do'`),
`type_text` before a focus checkpoint, and — worst — thinking mode set
`sends: false` on an explicit "reply to priya saying…", the consent bit the
send-approval flow hangs on. It also parsed Hinglish "whatsapp kholo" as a
person named "Kholo" and inverted "khaana kha chuka hoon" (already eaten)
into "I'm hungry". The BFCL win does not transfer to our protocol.

## Caveats recorded

- Greedy decode, no repetition penalty (prod behavior; LiquidAI's defaults
  include `repetition_penalty 1.1`). This does not explain reasoning in the
  answer channel or the sends/Hinglish errors.
- bf16 untested: the failures are behavioral, not quantization artifacts.
- `mlx-community/LFM2.5-2.6B-8bit` is a broken conversion today (missing
  `block_ff_dim`, `language_model.`-prefixed weights). Official
  `LiquidAI/LFM2.5-2.6B-MLX` works but is a 20 GB all-quants repo, so the
  registry would need filtered downloads if a Liquid model is ever adopted.

## Round 2 — owner pushback: "it's open source, something can be done"

Deep-researched (3 parallel agents: vendor/community fixes, HF ecosystem,
academic techniques) and tested the candidates locally. Verdict unchanged.

**No fix exists upstream.** Liquid's Head of Post-Training, on the record:
"this model is a pure reasoning model so it's not possible to deactivate
it" — their answer is the separate Instruct checkpoint, which exists only
at 1.2B. No 2.6B Instruct is announced. Zero no-think/instruct community
mods of the 2.6B exist on HF (the model is hours old; the 1.2B ecosystem
has 100+ fine-tunes, none de-thinking a reasoner). llama.cpp's LFM2.5
handling — written by a Liquid engineer — is strip-after-generation: the
thinking tokens are always paid for.

**bf16 / other quants change nothing** — the behavior is training, not
precision. Every mlx-community 2.6B conversion is broken anyway (mlx-vlm
0.6.10 batch: missing `block_ff_dim`, `language_model.`-prefixed weights;
I verified the 8-bit produces newline garbage after local repair).
Official `LiquidAI/LFM2.5-2.6B-MLX` subfolders are the only healthy MLX
weights.

**Best-known technique, tested here.** Prefilling a short fake trace
("Okay, I have finished thinking.\n</think>") — the arXiv:2504.09858
"NoThinking" recipe, and the only technique with a measured win on an
LFM2.5 model elsewhere — genuinely helps: probe cases went 1/5 → 4/5,
runaway timeouts disappeared. But the full 26-case harness still failed
**19/26 vs Qwen's 0/26** (answers dictated questions instead of
transcribing them, ignores romanization, drops list intros and content
words, misses number conversions), and Action Mode still failed 5/9
turns with the same wrong `sends` bits and protocol malformations.
Budget-forced thinking (128-token cap + cushioned close) scored worse
(2/5 probes) at 4-6× the latency.

**The build-it-ourselves path is real but not worth it.** LFM2.5-2.6B-Base
exists for exactly this; mlx-lm LoRA demonstrably works on the lfm2
architecture (community text2sql fine-tune trained and fused on Apple
Silicon); the LFM license permits fine-tune + redistribution below $10M
annual revenue. But the harness failures above are task-competence gaps,
not just thinking leakage — an SFT would have to teach transcription
discipline, list formatting, romanization, and Hinglish, i.e. build and
maintain our own instruct model to maybe reach what Qwen3.5-4B gives
today for free.

**What we keep:** the think-close hardening + local-path benchmarking
(committed), and this harness as a standing re-audit trigger.

## What would change the verdict

An **LFM2.5-2.6B-Instruct** (non-reasoning) release with comparable scores
— Liquid ships Instruct variants at other sizes, so watch for it. The
speed profile measured here (TTFT 91ms, p50 337ms with the fake trace,
prefill 3.6×, 38% less RAM) would beat Qwen meaningfully if the quality
gap closed. Re-run `scripts/benchmark_cleanup_quality.py` + the action
eval against any such release.

## Kept hardening from this audit

- `cleanup.py::_prompt_tokens` renders the template to text, closes any
  dangling `<think>`, then encodes — byte-identical for Qwen (verified),
  defends against reasoning-forced templates.
- `models.py::ensure_downloaded` accepts an absolute path to a local model
  directory, so unpublished conversions can be benchmarked with the real
  engine harness.
